# Project review — 2026-09-05

**Status:** Open findings from a source review. This document records risks;
it does not claim that they have been fixed or that public-beta blockers are
closed.

## Findings

### High — locking retains sensitive renderer data

`app_lock` zeroizes the Rust-resident database master key, but the frontend
lock mutation only invalidates the app-status query. Existing TanStack Query
records (clients, cases, tasks, finance, search, and attachment metadata)
remain in the renderer heap after the lock screen is displayed.

**Required correction:** On a successful lock, clear data-bearing frontend
queries and then refresh only the app-status query. Add a test that loads a
legal-record query, locks the vault, and verifies that the query cache no
longer contains that data.

### Medium — device-resume locking is not guaranteed

The shell requests a lock on `visibilitychange` only when the document becomes
visible. A device can sleep and resume without that visibility transition; if
the configured inactivity timer has not elapsed, the vault remains unlocked.

**Required correction:** Add a native, platform-appropriate resume signal (or
another reliable lifecycle mechanism) that locks the vault on every resume,
and validate it on Windows and macOS as required by the security plan.

### Medium — backup checksum validation is incomplete

Backup validation verifies only names listed in `checksums.json`. It does not
require a checksum for `database.sqlite`, reject an empty/partial checksum
map, reject duplicate ZIP names, or ensure that every `attachments/` entry is
covered before extraction.

**Required correction:** Validate one exact archive inventory: exactly one
database entry, one manifest, one checksum file, and a checksum-map key for
every database/attachment entry with no extras or duplicates. Add malformed
archive tests for missing database checksums, unlisted attachments, and
duplicate names.

### Medium — selected-document source tokens outlive a lock

One-use native-picker tokens, including their source paths, remain in
`AppState` until used. The picker command also does not first require an
unlocked vault. A source selected before lock can therefore be imported after
a later unlock.

**Required correction:** Require an unlocked vault before opening the picker,
clear pending source tokens during lock, and test that old tokens fail after a
lock.
