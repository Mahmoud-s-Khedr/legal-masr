# LegalMaster Solo UX review

Review date: 2026-09-06. Repository baseline: `7f8f22c`, with the existing working tree. Scope: review and recommendations only; no application behavior changed.

## Executive assessment

LegalMaster Solo has a suitable foundation for an individual Egyptian lawyer: a local workspace, Arabic-first navigation, recognizable record types, case-scoped hearings, managed attachments, and a deliberately simple financial model. The strongest design choices are the persistent search field, explicit archive explanations for clients and powers of attorney, contextual attachment panels, and a hearing-decision form that can also schedule the next hearing.

The main UX concern is whether a lawyer can trust the interface to show all work and complete a legal workflow without losing context. Current source contains missing event indicators, incomplete record links, inaccessible editing paths, misleading empty states, and forms that can fail validation without explaining why. These deserve attention before a visual redesign. The review does not establish readiness for unsupervised daily use.

The five highest-value improvements are:

1. Make deadlines and hearings visible, identifiable, and directly actionable from Today, the calendar, and case files.
2. Complete case identity and relationship editing: official number, client capacity, and client-owned power of attorney.
3. Distinguish loading, empty, failed, and missing states; make failed saves recoverable and visible.
4. Protect unfinished work during navigation, modal dismissal, and locking.
5. Make backup recovery understandable and demonstrably usable on a replacement computer.

These are recommendations for subsequent scoped work, not authorization to expand the implementation phase or add features outside the product plan.

## Product fit and workflow coverage

The [product requirements](plan/01-product-requirements.md) define the primary user as a solo Egyptian lawyer, potentially unfamiliar with technical software. Evaluate screens by whether they answer practical questions: Which case? Which court? What must I prepare? What happened? What comes next? What was paid? Can I recover my records?

## Priority definitions

- **P1 — before relying on daily work:** risk of missed work, wrong-record association, lost input, or a core workflow being unavailable.
- **P2 — before broader beta:** frequent friction, unclear recovery, accessibility, localization, or discoverability gaps.
- **P3 — refinement:** presentation and efficiency improvements after workflow reliability.

Priorities are reviewer judgments, not measured incident rates. No P0 is assigned: this review did not demonstrate production data loss or a security incident.

## Findings: daily work and case management

### UX-01 — Calendar days can hide tasks entirely · P1 · Confirmed in source

In `MonthGrid`, only hearings produce event labels. The overflow label appears only when the combined hearing/task count exceeds two. A day with one or two tasks and no hearings therefore has no event marker. `AgendaPage` also loads `ALL` tasks and reduces each task to its title, losing completion state and identity in the displayed calendar model.

**Consequence:** the month view can look free despite outstanding work; completed tasks can also be counted like actionable work.

**Recommendation:** show a task indicator even for a single task, preserve task IDs and completion state, and define an explicit completed-task visibility rule. Include the full date and event counts in each day's accessible name.

**Acceptance:** test days with zero events, one task, two tasks, one hearing plus one task, overflow, completed tasks, and duplicate task titles. Every outstanding task is discoverable without guessing which apparently empty day to open.

Evidence: [AgendaPage.tsx](../src/features/hearings/pages/AgendaPage.tsx), `items`, `MonthGrid`, day-detail rendering.

### UX-02 — Record links and Add actions do not complete their promise · P1 · Confirmed in source

Today links to `?hearing=id` and `?task=id`, but the destination pages do not read those parameters. The shell and Today “Add hearing/task” links open the destination page without opening its creation form. Today hearings may still be visible on the selected day, but the requested record is not selected or focused.

**Recommendation:** define route behavior for creation and record selection; carry the relevant case/date/client, select the appropriate view, and focus the requested record or editor. Provide a missing-record state for invalid IDs.

**Acceptance:** every Today record opens the exact item; Add opens a ready-to-use form; an old, future, completed, or missing item cannot silently land in an unrelated default view.

Evidence: [DashboardPage](../src/features/dashboard/pages/DashboardPage.tsx), [Shell](../src/components/layout/Shell.tsx), [AgendaPage](../src/features/hearings/pages/AgendaPage.tsx), [TasksPage](../src/features/tasks/pages/TasksPage.tsx).

### UX-03 — Saved hearings have no reachable edit action · P1 · Confirmed in source

The agenda supports a `HearingDto` editing state and a form with initial values, but no rendered action sets that state to an existing hearing. The case hearings tab is a plain list. The next-hearing helper says copied details can be edited later, while the inspected UI offers no path to do so.

**Recommendation:** add a visible edit action alongside decision recording; show case identity, date, court, circuit, and preparation requirements before committing an outcome.

**Acceptance:** create a hearing, correct its date/court/time, record a decision with a next hearing, and independently edit the new hearing. Failed saves retain the draft and explain the next step.

Evidence: [AgendaPage](../src/features/hearings/pages/AgendaPage.tsx), `editing`, `HearingForm`, `DecisionForm`; [CaseDetailPage](../src/features/cases/pages/CaseDetailPage.tsx).

### UX-04 — Today provides too little context for preparation · P1 · Confirmed in source

Today hearing rows show type, time, and location without case number, client, circuit, or required documents. The dashboard does not render the `upcomingHearings` field available in its summary type. Overdue tasks are text rather than links. The first five clients/cases occupy space without an explained selection rule.

**Recommendation:** prioritize today's actionable rows and overdue tasks, followed by tomorrow/upcoming preparation. Display case/client context and a preparation excerpt. Make overdue items actionable. Keep general record shortcuts secondary.

**Acceptance:** with several hearings of the same type, the lawyer can distinguish each case and open its required preparation. Upcoming work appears without opening the calendar. The page distinguishes failed loading from a genuinely free day.

Evidence: [DashboardPage](../src/features/dashboard/pages/DashboardPage.tsx), [bridge types](../src/bridge/types.ts), `DashboardSummary` fields.

### UX-05 — Case identity is incomplete and misleadingly labeled · P1 · Confirmed in source

`CaseCoreFields` edits `internalNumber` under the translated label “رقم القضية”. It has no input for `officialNumber`, although the schema and edit defaults contain it. The list presents the internal number beside the official year, which can look like an official case reference. The client table similarly labels the internal-number column “النوع”.

**Recommendation:** explicitly separate “رقم الملف الداخلي” from “رقم القضية بالمحكمة”, with official year and court grouped together. Correct the client column to “الرقم الداخلي”. Keep identifiers directionally isolated.

**Acceptance:** users can enter and edit both case identifiers independently; list/detail/search displays identify which number is shown. A case without an official number remains valid and clearly labeled.

Evidence: [CaseCoreFields](../src/features/cases/forms/CaseCoreFields.tsx), [CaseListPage](../src/features/cases/pages/CaseListPage.tsx), [ClientListPage](../src/features/clients/pages/ClientListPage.tsx), [Arabic resources](../src/i18n/ar/common.json).

### UX-06 — Case client relationships cannot be maintained through the UI · P1 · Confirmed in source

Creation collects client IDs only. `CaseClientsPanel` displays relationships without editing controls. Case editing preserves existing relationship attributes, so it cannot add/remove clients or set their legal capacity and client-owned POA through the inspected form.

**Recommendation:** provide a relationship editor within the case. Use client ID for identity, show internal number beside names, and restrict POA choices to the selected client's valid relationships through the existing typed service boundary.

**Acceptance:** create a multi-client case with distinct capacities and POAs; change one relationship without changing another; explain incompatible POA and payment-related removal failures without discarding input. Add normal and failure-path business-rule tests during implementation.

Evidence: [CaseCreateForm](../src/features/cases/forms/CaseCreateForm.tsx), [NewCasePage](../src/features/cases/pages/NewCasePage.tsx), [CaseClientsPanel](../src/features/cases/components/CaseClientsPanel.tsx), [CaseDetailPage](../src/features/cases/pages/CaseDetailPage.tsx).

### UX-07 — Client POAs are associated by name in the display · P1 · Confirmed in source

`ClientDetailPage` determines linked POAs using `poa.clientNames.includes(item.fullName)`. Two clients with the same full name can therefore see one another's POAs in this view. This is a display association defect; this review does not claim the stored relationship is corrupted.

**Recommendation:** obtain or filter relationships by stable client ID. If a typed query change is required, keep it behind the bridge.

**Acceptance:** create two same-name clients with separate POAs. Each detail page shows only its own relationships, including after a rename and with the intended archive policy.

Evidence: [ClientDetailPage](../src/features/clients/pages/ClientDetailPage.tsx), `linkedPowers`.

### UX-08 — Case status filters contain values outside the canonical form model · P2 · Confirmed in source

The list offers DRAFT, JUDGMENT_ISSUED, APPEALED, and ENFORCEMENT in addition to the canonical ACTIVE, SUSPENDED, and CLOSED states. A TypeScript cast does not make those options valid domain values. Runtime service behavior for the extra values was not exercised.

**Recommendation:** use the canonical states with Arabic labels, keeping litigation degree separate from case status.

**Acceptance:** every offered filter corresponds to a supported saved state and has a clear label; no unsupported value is sent.

Evidence: [CaseListPage](../src/features/cases/pages/CaseListPage.tsx), [case schema](../src/features/cases/schemas/case.schema.ts).

## Findings: reliability, forms, and recovery

### UX-09 — Loading failures can look like “nothing to do” or zero money · P1 · Confirmed in source

Today, tasks, finance, list pages, and record detail pages frequently render `data ?? []`, zero totals, or “not found” without a distinct query-error branch. The startup gate treats absent status as loading indefinitely. Settings already demonstrates a better explicit load-error/retry pattern.

**Recommendation:** standardize loading, successful-empty, filtered-empty, failed, and genuinely missing states. Never imply a zero balance or free day while data is unavailable. Preserve usable cached data with a clear refresh-failed message where appropriate.

**Acceptance:** inject query failures into each primary page; show a meaningful retry action and preserve context. Startup status failure offers recovery rather than endless loading. A restored connection or successful retry recovers the current view.

Evidence: [App](../src/app/App.tsx), [DashboardPage](../src/features/dashboard/pages/DashboardPage.tsx), [FinancesPage](../src/features/finances/pages/FinancesPage.tsx), [ClientDetailPage](../src/features/clients/pages/ClientDetailPage.tsx), [SettingsPage](../src/features/settings/pages/SettingsPage.tsx).

### UX-10 — Form validation can reject submission without explaining why · P1 · Confirmed in source

Client and case forms use schema validation but do not render field errors. A case with no selected clients fails the schema's minimum-one-client rule without a corresponding message. On a fresh installation, the case form provides neither clients nor an actionable empty state. Whitespace-only required text can pass native required checks but fail trimmed schema validation.

**Recommendation:** show field-level errors, an accessible summary when useful, and a create-client route that preserves the case draft. Explain required and optional fields before submission. Focus the first invalid input.

**Acceptance:** no selected clients, whitespace-only names/numbers, and service validation failures each yield a specific message and recoverable form. Successful submission is clearly acknowledged.

Evidence: [ClientForm](../src/features/clients/forms/ClientForm.tsx), [CaseCreateForm](../src/features/cases/forms/CaseCreateForm.tsx), [case schema](../src/features/cases/schemas/case.schema.ts).

### UX-11 — Unfinished work is unprotected across navigation and dismissal · P1 · Confirmed in source / runtime loss paths need testing

No dirty-form navigation guard or `beforeunload` handling was found in `src`. Shared dialogs dismiss on Escape and backdrop clicks. Switching detail tabs unmounts editors. Shell locking can unmount the workspace; its visibility listener requests a lock whenever the document becomes visible when lock timeout is enabled, regardless of measured elapsed time.

**Recommendation:** provide consistent discard/stay behavior for voluntary navigation and dialog dismissal. For mandatory security locking, design secure draft preservation without delaying required locking or putting legal data in unprotected browser storage. Validate visibility transitions with native pickers and app switching before changing lock policy.

**Acceptance:** dirty drafts survive or prompt appropriately on tabs, sidebar, Cancel, Escape, backdrop, window close, manual lock, and idle lock. Sensitive fields remain protected. Returning from a native dialog does not unexpectedly discard work.

Evidence: [Dialog](../src/components/ui/Dialog.tsx), [Shell](../src/components/layout/Shell.tsx), detail/edit pages.

### UX-12 — Several mutations have no visible failure or pending feedback · P1 · Confirmed in source

Tasks display save errors but not completion/reopen/delete errors. Case archival, client updates, fee saves, and opponent removal have uneven feedback. Confirmation actions lack a shared pending state, allowing repeated clicks while an operation is in progress.

**Recommendation:** make pending, success, and failure behavior explicit per operation. Keep failed edits open. Prevent duplicate submission. Use undo for reversible actions where appropriate; retain consequence-specific confirmation for permanent removal.

**Acceptance:** simulate rejected completion, archive, removal, and fee-save operations. The visible state remains truthful, retry is possible, and no duplicate action is submitted. Use persistent inline errors for actions requiring correction.

Evidence: [TasksPage](../src/features/tasks/pages/TasksPage.tsx), [CaseDetailPage](../src/features/cases/pages/CaseDetailPage.tsx), [ClientDetailPage](../src/features/clients/pages/ClientDetailPage.tsx), [CasePartiesPanel](../src/features/cases/components/CasePartiesPanel.tsx), [ConfirmDialog](../src/components/ui/Dialog.tsx).

### UX-13 — First-record creation loses momentum and context · P2 · Confirmed in source

Creating a client or case navigates back to its list. “Add case” from a client file does not pass the client context. Both case and POA forms render the full client collection as checkboxes.

**Recommendation:** open the newly created detail page, with a clear next action such as add case or hearing. Prefill originating client context and use a searchable multi-select with names and internal numbers. Preserve selected entries when filtering.

**Acceptance:** first client and case can be created within the plan's ten-minute target without re-finding either record; a 500-client fixture remains usable without scrolling through all checkboxes. This is a proposed acceptance target, not a measured result.

Evidence: [NewClientPage](../src/features/clients/pages/NewClientPage.tsx), [NewCasePage](../src/features/cases/pages/NewCasePage.tsx), [ClientDetailPage](../src/features/clients/pages/ClientDetailPage.tsx), [PowerOfAttorneyForm](../src/features/powersOfAttorney/components/PowerOfAttorneyForm.tsx).

### UX-14 — Recovery needs a clearer exit and stronger setup assistance · P2 · Confirmed in source

Setup has one password field and no visibility toggle or confirmation. The recovery page has no visible way back to unlock. The once-shown recovery key has an acknowledgment button but no dedicated copy/save assistance. Schema errors are not rendered in these forms.

**Recommendation:** explain the password requirement before typing, support deliberate password visibility and confirmation, provide a return-to-unlock action, and make secure recovery-key recording understandable. Any clipboard/export assistance must explain its privacy implications and avoid logging secrets.

**Acceptance:** a first-time user can explain the difference between password and recovery key, correct setup errors, leave recovery without restarting, and complete wrong-password/wrong-key recovery tests without losing state unexpectedly.

Evidence: [OnboardingPage](../src/features/onboarding/pages/OnboardingPage.tsx), [App](../src/app/App.tsx).

## Findings: Arabic, accessibility, and navigation

### UX-15 — English mode and domain terminology are incomplete · P2 · Confirmed in source

Many pages hardcode Arabic while language switching sets the document to English/LTR. Litigation degree choices display raw constants such as `FIRST_INSTANCE`; case hearing/status summaries also expose raw enum values. “العملاء” and “الموكلون” are used inconsistently.

**Recommendation:** complete translation coverage for shipped language choices, localize enum labels, and define a short domain glossary. Preserve Arabic-first behavior and separate visible labels from stored values.

**Acceptance:** walk every route in both languages with no raw keys/constants or unintended mixed-language chrome. Use “الموكل”, “الخصم”, “الصفة في القضية”, and explicit internal/official identifiers consistently.

Evidence: [i18n](../src/i18n/index.ts), [CaseCoreFields](../src/features/cases/forms/CaseCoreFields.tsx), [CaseDetailPage](../src/features/cases/pages/CaseDetailPage.tsx), dashboard/task/finance pages.

### UX-16 — Arabic money entry is less capable than Arabic money display · P1 · Confirmed in source

`parseMoneyToMinor` accepts ASCII digits and a limited decimal format. It rejects Arabic-Indic digits and the Arabic decimal separator, while display uses Arabic Egyptian currency formatting. Grouped pasted amounts also lack a clear supported policy.

**Recommendation:** normalize supported Arabic and Latin digits/separators before exact minor-unit parsing. Reject ambiguous input explicitly instead of guessing. Keep integer minor units and safe-integer validation; do not introduce floating-point financial storage.

**Acceptance:** cover `123.45`, `١٢٣٫٤٥`, supported Persian digits if included, paste behavior, zero, negatives, more than two decimal places, ambiguous grouping, and overflow. Equivalent accepted inputs produce the same minor units.

Evidence: [FinancesPage](../src/features/finances/pages/FinancesPage.tsx), `parseMoneyToMinor`.

### UX-17 — Saved date/week preferences are not applied by the inspected views · P2 · Confirmed in source

Settings offers date format and week start. Agenda hardcodes a Saturday week start and Arabic month formatting; several views output raw ISO dates. Date-only storage is appropriate, but presentation should honor the preference without timezone conversion.

**Recommendation:** centralize date-only presentation, apply week start consistently, and retain stable internal date strings. Give previous/next controls labels matching the active view; the list currently retains period controls without filtering its all-date list.

**Acceptance:** changing format/week start updates Today, agenda, tasks, and record dates; no date changes across timezone/DST tests. List navigation either changes the list period or is removed for that view.

Evidence: [SettingsPage](../src/features/settings/pages/SettingsPage.tsx), [AgendaPage](../src/features/hearings/pages/AgendaPage.tsx), [dateOnly](../src/lib/dateOnly.ts).

### UX-18 — Shared tabs change selection without moving focus · P2 · Confirmed in source

`Tabs` handles arrows and Home/End by changing the selected value but does not move DOM focus, implement roving tab stops, or connect tabs to panels. Case details implement another button-navigation pattern. Source inspection also found no shared route-focus or skip-to-content mechanism.

**Recommendation:** implement one consistent accessible tab pattern, appropriate focus movement, panel relationships, and deliberate RTL arrow behavior. Move focus meaningfully after route navigation and provide a main-content shortcut.

**Acceptance:** keyboard users can identify the selected tab, move focus and selection predictably, reach its panel, and return from dialogs. Test both RTL and LTR with a screen reader; unit tests alone cannot establish usability.

Evidence: [Tabs](../src/components/ui/Tabs.tsx), [CaseDetailPage](../src/features/cases/pages/CaseDetailPage.tsx), [Shell](../src/components/layout/Shell.tsx).

### UX-19 — Accessible names and dialog error placement need consistency · P2 · Confirmed in source

List search inputs rely on placeholders rather than explicit labels. The case fee input has no label. Generic attachment actions repeat without record-specific accessible context. Attachment mutation errors appear outside the portal dialog where the form is being edited, which can make them difficult to discover while modal focus is active.

**Recommendation:** label every field, associate error/help text with fields, give repeated actions contextual names, and put form failures inside the active dialog. Retain visible focus styling and the existing modal focus-return behavior.

**Acceptance:** a screen-reader field list identifies every input; errors are announced in the active interaction; repeated “فتح” actions identify their target document. Test focus containment and background interaction in the real desktop webview.

Evidence: [ClientListPage](../src/features/clients/pages/ClientListPage.tsx), [PowersOfAttorneyPage](../src/features/powersOfAttorney/pages/PowersOfAttorneyPage.tsx), [CaseDetailPage](../src/features/cases/pages/CaseDetailPage.tsx), [AttachmentPanel](../src/features/documents/components/AttachmentPanel.tsx), [Dialog](../src/components/ui/Dialog.tsx).

### UX-20 — Global search conflates waiting, failure, and no results · P2 · Confirmed in source

Search reads only query data and displays no-results when none is available. Escape handling returns early when there are no selectable hits, leaving the empty popup open until another dismissal occurs. Active result indices are not explicitly reconciled when result data changes. Search scope is clients, cases, and POAs; the UI should not imply document/task content search.

**Recommendation:** distinguish pending, empty, and failed results, make Escape unconditional, keep active selection valid as results change, and state supported search scope. Keep the existing grouped results and keyboard support.

**Acceptance:** rapid typing, delayed results, zero results, errors, keyboard selection, Escape, and shrinking result sets behave predictably. Test the product's promised lookup terms against actual results separately; this review did not validate backend search recall.

Evidence: [GlobalSearch](../src/features/search/components/GlobalSearch.tsx).

### UX-21 — Navigation does not resolve document and backup discoverability · P2 · Confirmed in source / product decision

The router contains `/attachments` and `/backups`, but neither is in `NAV_ITEMS`. Backup controls are reachable in Settings, so backups are not wholly inaccessible. Attachments are available on record tabs; the standalone route expects owner parameters and does not provide a global document browser. The product requirements still list documents and backups as primary navigation destinations.

**Recommendation:** reconcile navigation with the current product plan. Add a visible backup shortcut/status. Decide whether documents remain explicitly record-scoped or require the planned global index. Do not simply expose an ownerless upload page; preserve exactly one attachment owner.

**Acceptance:** a new user can find backup controls and a known case document without route knowledge. Any global document entry displays ownership clearly and requires a valid owner for adding files.

Evidence: [router](../src/app/router.tsx), [DocumentsPage](../src/features/documents/pages/DocumentsPage.tsx), [SettingsPage](../src/features/settings/pages/SettingsPage.tsx), [product requirements](plan/01-product-requirements.md).

## Findings: money, documents, and data confidence

### UX-22 — Case account does not answer the full fee question · P1 · Confirmed in source

The case account shows agreed and received amounts but does not render outstanding, expenses, or net cash, despite available summary fields. The agreement input is blank, unlabeled, and silently ignores invalid values; save has no visible pending/success/error state. A new finance entry does not inherit the currently filtered case/client because the forms receive no such defaults.

**Recommendation:** show agreed, received, remaining, expenses, and net with plain explanations; prefill the fee agreement; carry case context into new entries and keep payer eligibility explicit. Avoid presenting case debt as the personal debt of every linked client without an allocation rule.

**Acceptance:** a multi-client case has unambiguous totals; changing the selected case refreshes allowed payers; failed fee saves never look successful; adding from a filtered context starts with that context. Test normal and failure paths with integer minor units.

Evidence: [CaseDetailPage](../src/features/cases/pages/CaseDetailPage.tsx), [FinancesPage](../src/features/finances/pages/FinancesPage.tsx).

### UX-23 — File-picker cancellation and recovery are under-explained · P2 · Confirmed in source / native validation needed

`selectSource` awaits the native bridge without a local catch or cancellation branch. Save/open/reveal/remove failures share a broad message. The UI explains managed copies, which is valuable, but cannot tell users whether to choose the file again, retry opening, or correct metadata.

**Recommendation:** distinguish cancellation from failure, handle source-selection errors inside the modal, and give operation-specific recovery. Explain when reselecting a file is needed after a one-use token failure. Preserve metadata and the existing distinction between managed-copy removal and the original file.

**Acceptance:** cancel a picker, select an unavailable/unsupported source, fail a copy, retry, open a missing attachment, and cancel removal. Each path leaves an understandable state without duplicate records. Native behavior must be tested on Windows/macOS.

Evidence: [AttachmentPanel](../src/features/documents/components/AttachmentPanel.tsx), [functional modules](plan/04-functional-modules.md).

### UX-24 — Backup success is not yet a complete recovery experience · P1 · Confirmed UI limitations and documented gaps

The panel shows the latest successful backup, which is useful. It has no archive history, destination choice, archive-specific preview, or visible reveal/copy workflow. Restore confirmation occurs before the bridge's archive operation, without an in-panel summary of the selected archive. Privacy describes a generic app-data location rather than a usable location action. The plan explicitly records cross-device restore validation, scheduling, retention, and complete export as open.

**Recommendation:** distinguish local backup completion from protection against losing the computer. Offer constrained native destination/reveal actions, a readable date and file size, and a restore flow that identifies and validates the chosen archive before final replacement confirmation. Explain password requirements based on verified archive behavior. Prove portability before claiming it.

**Acceptance:** on disposable synthetic vaults, back up, copy to independent storage, restore on a replacement target device, verify records and attachments, reject corrupt/wrong-credential archives, and recover from interrupted restore without changing the original data. This is a separate implementation/release workstream requiring the existing backup/security criteria.

Evidence: [BackupsPage](../src/features/backups/pages/BackupsPage.tsx), [backup hooks](../src/features/backups/api/backupsApi.ts), [SettingsPage](../src/features/settings/pages/SettingsPage.tsx), [functional gaps](plan/04-functional-modules.md).

### UX-25 — Reminder settings exceed the visible per-record controls · P2 · Confirmed in source / delivery validation needed

Task and hearing forms have no reminder selector despite reminder fields in the typed model and a default lead-time setting. Settings usefully explains that a fully closed app does not deliver reminders, but the record itself does not show whether or when it will remind the lawyer.

**Recommendation:** show effective reminder behavior near the due date and permit supported overrides through existing commands. Explain disabled OS permissions and app-running requirements in context. Verify whether edits preserve existing overrides before claiming they do.

**Acceptance:** default, overridden, disabled-permission, locked, closed, resumed, and changed-date scenarios produce predictable feedback. Physical notification delivery remains a target-platform check, not a frontend-test claim.

Evidence: [TaskForm](../src/features/tasks/pages/TasksPage.tsx), [HearingForm](../src/features/hearings/pages/AgendaPage.tsx), [SettingsPage](../src/features/settings/pages/SettingsPage.tsx), [App](../src/app/App.tsx).

## Visual hierarchy and plain-language improvements

These are P3 refinements unless testing finds that they prevent access to a core action.

The historical screenshot shows a coherent green/cream palette, a recognizable right sidebar, generous spacing, and prominent primary actions. Preserve this general direction. The current stylesheet already includes logical-direction properties, visible focus outlines, local Arabic font choices, dark/system themes, and responsive rules. Their presence is a strength, but does not prove contrast, zoom, or webview rendering quality.

The screenshot dedicates considerable upper-page space to the title, general metrics, and action buttons; urgent details extend toward/beyond the lower edge. That exact layout is historical. For fresh captures, judge the first viewport by how many actionable hearings/deadlines are understandable, rather than how many cards fit.

Several helper styles use approximately 0.7–0.75rem text. Test Arabic legibility on normal laptop displays and at increased scaling. Inspect long Arabic names, mixed filenames, legal identifiers, native date controls, dark-theme button contrast, focus indicators, and modal scrolling. No measured contrast failures or current viewport-overflow claims are made here.
